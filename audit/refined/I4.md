## Questions
1. Clear typed inputs after Apply, as legacy did? — (a) clear every input and reset enums/toggles to baseline after each Apply response (legacy `functions.js:32-36`) → nothing is re-sent unintentionally; a rejected value must be retyped; (b) clear the fields answered Valid/Unchanged and reset enums/toggles, keep Invalid/Failed inputs for correction → no silent re-send of `ForceCalRef`/`AmbPres`/`SystemCmd`, corrections stay easy; (c) keep typed values (today) → every later Apply of the card re-sends them: another FRC recalibration, another NVM write, a repeated `SystemCmd`. Recommendation: (b), legacy's intent with no functional loss. (RF346)
2. Readable labels for status codes like `reset_reason`? — (a) numbers only, except OR76.a's ISL29125 code → catalogue renumbering touches fixtures only; users look codes up in the docs; (b) a plain-language label for every published status code (`reset_reason`, the ISL29125 code, …) from its `@web` tag → readable diagnosis; renumbering updates tags, still one source; (c) (b) plus labels for errcount history `num` codes → most readable; conflicts with A28's colour-only history and grows the bundle. Recommendation: (b). (RF340)
3. How should the page show a stale reading? — (a) as today: last good value with a bare-integer timestamp → a frozen reading cannot be told from a live one; (b) the page shows each sample's age from its `TS` against `UtcTime` and formats timestamps as dates, API unchanged → staleness visible; ISL29125's `None` rule stays, documented beside it in Part H; (c) every driver publishes `None` for a sample it cannot prove current, like ISL29125 → one API semantics; an API behaviour change and the last good value is lost. Recommendation: (b). (RF333)
4. Show terminal WLAN deactivation on the status LED? — (a) keep plain off → an operator cannot tell "power-cycle me" from "still trying"; (b) a distinct LED pattern for the deactivated and missing-configuration states, honouring `LedWifiOn` → visible locally at no API cost; needs a pattern distinct from the hotspot flash; (c) signal it on the NeoPixel where one is wired → richer, but only on devices with a NeoPixel. Recommendation: (b). (RF336)
