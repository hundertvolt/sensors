## Questions
1. Declared FRAM chip dead: contain, or escalate to reboot? — (a) contain as today (RAM-only logs, SGP40 without backup; G5/R32's "no module insist on FRAM", owner 2026-08-11, read to cover it) → runs indefinitely without persisted evidence; OR18.a gets a stated FRAM exception, and the manager must stop touching a chip whose setup failed, or the ring fills with per-access errors; (b) escalate like any chip (OR18.a, owner 2026-09-25, "a configuration not matching the hardware") → a stalled chip may recover, but a truly dead optional chip reboots the unit every few minutes, sensors down in between; (c) escalate once per power-up, then contain (a `mem_backup()` flag beside G5/R03's record) → one recovery chance, no reboot loop, one more reset-reason code. Recommendation: (c); (a) if simplicity wins, with the manager going quiet after a failed setup. (RF153)
2. Status page: show error text, or bare numbers? — (a) numbers only (today) → the C.7.1 catalog is the reader's key; OR28.a (3)'s "code-to-text mappings … updated" has nothing to act on; (b) the website shows text from a table generated from C.7.1 at build time, `/status` unchanged → readable Status page, no device RAM cost, a little frozen-HTML flash, an agreement test against the catalog; (c) `/status` carries the text → every client gets it, at a RAM and response-size cost per entry on the device. Recommendation: (b). (RF151)
