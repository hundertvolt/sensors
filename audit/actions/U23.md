## Recovery ladder (brief rule 8, OR113.a (2)) — the website's fault paths

The website has no bus; its participant is the device's REST server, reached one request at a time. Rungs, smallest
first, each bounded and logged once per event: (1) retry — a failed GET is retried on the next tick of its section, with
the interval doubling per consecutive failure up to 60 s (A.U23.05), so a rebooting or overloaded device (the server
saturates near 2.2 requests/s; OR114.a's override makes a stuck write wait cooperatively up to the 5 s per-call timeout) is
never hammered; a settings page retries until one success; one banner and one console line per failure episode;
(2) bound — every request, body included, ends by the 15 s client timeout equal to `outer_cap_s` (A.U23.02), and a left
section's work is aborted (A.U23.03), so one stalled request never blocks another section; (3) recover the page's view of
the device — after a failure episode ends, the device watch re-reads `/status` and `/system` (A.U23.06); (4) reload — a
changed build reloads the page (A.U23.06); (5) the user — a PUT is never retried (OR42.a (3)); its failure is shown per
field and the typed values stay for correction (A.U23.15). Tests at every level that reaches them: L0 fake-timer tests
(A.U23.02-A.U23.06), L2 live restart recovery (A.U23.35) and full-ceiling tabs with reload recovery (A.U23.34); L4 is the
cross-browser smoke's single session (U28/U6), no new bench rung. OR114/OR115 need no website change: the page adds no
TCP option, keeps its timeout equal to the server's cap, and its back-off does not amplify a stall.
