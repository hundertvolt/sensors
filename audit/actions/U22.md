### A.U22.01 Every LED task (re)starts into a defined pixel state
- **Why**: brief rule 8 / OR113.a (2) — "every fault on a bus, a participant or a service recovers with the smallest
  possible blast radius … retry; recover the participant; … restart the task; reboot; watchdog last — at boot and
  mid-operation, each rung bounded, logged once per event, race-free, tested at every level that can reach it" (owner,
  2026-09-30, OR113 "Apply this idea throughout!"); G3/R64 (pilot: "a signal cancelled mid-ramp leaves no lit pixel and
  no set event to replay"); the U9 pilot predates OR113 and SUPP_recovery does not cover LED.
- **Site**: `src/asy_neopixel_driver.py:70-77` `_led_overl_signal()`, `:155-158` `neopixel_signal()` start; SPEC A.4
  NeoPixel paragraph (`:252-257`).
- **Change**: the ladder, from source: the WS2812 is write-only — `NeoPixel.write()` is one `machine.bitstream()` call
  (`mplib/micropython/drivers/led/neopixel/neopixel.py`, `write()`), which raises only for bad arguments
  (`extmod/machine_bitstream.c:39-60`, v1.29.0) that A.U9.06's sanitiser excludes; `ports/rp2`'s
  `machine_bitstream_high_low()` returns nothing (`ports/rp2/machine_bitstream.c:52`). No participant fault is
  observable, so rungs R1-R4 (retry, participant, bus, controller) have no trigger; the ladder starts at the task: any
  end of the overlay or signal task is restarted by the supervisor (`src/system_service.py:232-239`, R5), reboot and
  watchdog above it (U11). What this action adds is the defined state at each (re)start: (a) `_led_overl_signal()` calls
  `self.led_overl_start.set()` once before its `while True:` — a `ThreadSafeFlag` set before `wait()` makes that wait
  return at once (`extmod/asyncio/event.py`, `ThreadSafeFlag.wait()`), so a (re)started overlay task re-applies the
  current overlay (`led_overl_on`, brightness) under the overlay lock instead of leaving whatever the pixel last showed
  until the next `on()`/`off()`; (b) `neopixel_signal()`'s start (`:157-158`, black) gains
  `self.led_overl_start.set()` after the black write — the same restore its normal end already does (`:187`), so a
  restarted signal task does not leave the WiFi LED dark. Both writes are synchronous with no `await` between setting a
  frame and `write()`, so no other task can interleave a half frame. Nothing is logged here: the supervisor already
  logs each restart once (its restart warning, one entry per task end, A.U3.06). SPEC A.4's NeoPixel paragraph gains:
  "The pixel reports no faults (`machine.bitstream()` raises only for bad arguments, which the driver's sanitiser
  excludes), so its recovery is the task's: the supervisor restarts an ended overlay or signal task, and each (re)start
  writes a defined state — the signal task black, then the overlay restored; the overlay task the current overlay
  (agent, 2026-09-30)."
- **Blast**: callers the supervisor (restarts the starters from `get_task_starters()`) · generated — · js — · tests
  existing: the overlay and signal tests in `tests/test_asy_neopixel_driver.py` start both tasks, which now each write
  one frame more at start (the current overlay, `(0, 0, 0)` while off) — checked: every `writes[-1]` assert holds, the
  two count-based tests hold (`:140-155` counts relative to a snapshot taken after the tasks started; `:386-401` asserts
  `>= 30`), and no test asserts `writes[0]` or an absolute count (grep `len(.*writes\|writes\[0\]` over the four LED
  test files: only those two); new: L1 `tests/test_asy_neopixel_driver.py` — (1)
  overlay on, overlay task cancelled and a new one started: the pixel shows the overlay colour again with no further
  `on()` (condition wait on `writes`, bounded by `l1.asy_neopixel_driver_overlay_settle_s`); (2) overlay on, the signal
  task ended by `raise_on_write` (the unit fake's own injection, `tests/neopixel.py`) mid-ramp and restarted: black,
  then the overlay colour, and no frame of the old ramp colour after the restart; (3) the same through a real
  `SystemService` supervisor loop over the driver's starters (the supervisor's own test harness pattern in
  `tests/test_system_service.py`, read at execution): the task restarts, the restart warning is logged once; new L2: a
  booted twin device whose `digital_twin/neopixel.py` fake gains a `raise_on_write` injection (U25 owns the fake) — the
  signal task restarts and the pixel ends dark with the overlay restored · twin as above · docs SPEC A.4 as above;
  BACKLOG — (no hardware row: the pixel has no fault to inject on silicon, OR45.a (3)'s listed-exception path —
  recorded in the E.6 exception list by U35/U36) · toml — · uart —.

### A.U22.03 Wake the LED-pause task on change, not every second
- **Why**: G4/R56 — "A task waiting for traffic that may never come polls at a slow, tuned idle interval, never at its
  transaction rate … every other poller follows the same pattern" (agent, 2026-09-26, an OR24 consistency change; UART
  idle rate `poll_idle_ms` "(agent, 2026-09-11)"); SPEC F.5.9 "An idle `ready()` poll is a permanent CPU cost, not a free
  wait"; REF/R03 (the pause counts measured time, A.U9.09). `auto_led_override()` wakes every second forever
  (`src/asy_notification_service.py:321-330`) although a pause is set only by a REST PUT, which may never come.
- **Site**: `src/asy_notification_service.py:317-330` `auto_led_override()`, `:273-274` `set_override_led()`,
  `NotificationCoordinator.__init__` (`:158-159`); as rewritten by A.U9.09 (`self._pause = TickSeconds(count_down=True)`).
- **Change**: new `self._pause_changed = asyncio.Event()`; `set_override_led(secs)` restarts `_pause` (A.U9.09) and
  sets the event. `auto_led_override()`: `while True:` — `secs = self._pause.read()`; `secs > 0` → the `_auto_active`
  False transition as today (one `evt`), then `await wait_for_ms(self._pause_changed.wait(), secs * 1000)` (A.U10.26's
  one timeout mechanism; a timeout is the normal expiry) and `self._pause_changed.clear()`; `secs == 0` → the True
  transition as today, then `await self._pause_changed.wait()` and clear. So with no pause the task sleeps on an event
  (zero wake-ups), during a pause it wakes once at its end (or when a new PUT changes it), and `_auto_active` flips at
  the measured end rather than up to one round late. The 1 s round and its tag `notify.loop_tick_s` (A.U8.12) go from
  this task (the tag stays if another site still uses it — `:330` is its only site in this file; grep at execution).
  `get_override_led()` is unchanged (reads measured time, A.U9.09). No `sleep(0)`, no interval poll remains in the file
  except `monitor_loop()`'s `Interv` period, which is the feature's own check cadence, not an idle wait.
