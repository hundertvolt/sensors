## Decisive for the plan, by item

- **B6 (UART), a real firmware bug.** `asy_uart_driver.py` stopped the receive ring with `DMA.active(False)` on the data
  channel chained to the reload. RP2040-E13 (datasheet p. 629, 2.5.5.3): an abort with transfers in flight completes
  as a normal completion; the completion fires the chain, the reload restarts the data channel, and the SDK's abort
  spins on BUSY for ever. USB dies, the watchdog resets. Every `deinit()`/re-`init()` with the ring armed (task restart,
  reconfig) reads as an unexplained watchdog reset. Located by SCRATCH0 step markers; probe-confirmed on silicon.
  Fix on the bench branch (916fb878, changelog B93): `_rx_stop()` sets CHAIN_TO to itself (2.5.7: disables chaining)
  through the non-triggering AL1_CTRL alias, then aborts reload and data. `tests/rp2.py`'s fake now raises where silicon
  hangs (16 old-driver tests fail). Run there: driver 174/174, comm 205/205, ruff. **Not run: mypy, the other tiers,
  the twin.** It lives only on the bench branch; R1's B6 carries it in, test first, through the hunk ledger.
- **B6, more.** (1) UARTRSR sees a line error only when the line then goes quiet: under glitches the driver flagged 8
  of 134 corrupted frames; `src/asy_uart_driver.py:80` ("OE, FE and BE each fail the frame") overstates it, and dev runs
  `crc = "none"`, so a right-length corrupted payload passes there. (2) `read()` without the session lock returns before
  `ready()`'s yield and spins the loop; `UARTComm` always holds the lock, but CLAUDE.md's "every read loop goes through
  `ready()`" has that hole. (3) Open: crc16 `next_ok` false after a cancelled read mid-train and `clean_after` false
  after the cmd sweep (seen in two runs). (4) Recovery 1.5-1.8 s against the 7 s bound; max transfer 12,192 B intact;
  idle poll works as designed. (5) `uart_dma_ring_interrupts_off.py`'s reader now drains during the stream (a test fix).
- **B2 (boot, reset reasons).** `reset_cause()` gives 3 for `machine.reset()`, a watchdog timeout and (stale) a soft
  reset; WATCHDOG REASON tells them apart (FORCE 0x2, TIMER 0x1). CHIP_RESET HAD_POR (0x100) stays set after watchdog
  resets until a power cycle: 0x100 with REASON non-zero is a watchdog reset, not a power-on. `mem_backup` survives
  `machine.reset()`, soft reset and watchdog; a BOOTSEL round trip (`picotool reboot`) loses both regions, cause 3,
  REASON TIMER. `bench/test_reset_reasons.py` expects ResetReason 4 there and fails as written.
- **B3 (FRAM) and the W29 read.** The dump (10-28 17:46, old firmware) holds 11 valid log chunks (both copies equal,
  status idle) and **no W29**. W29 can never be there: the FRAM module's log is RAM-only by design (SPECIFICATION C.7.1;
  `asy_fram_manager.py` builds `PrintLogHistory`, dev passes `log_ram`). Round 1's "FRAM log read for W29" is therefore
  unanswerable from the FRAM and should be restated; what it asked is answered by measurement instead: 2,182,266 RDIDs
  at 1 MHz, 0 mismatches, so the ID retries had no work on this bench. Entries present: W81 (`_WRN_WLAN_NO_VERDICT`,
  count 2), E21 (bad argument, count 1), W34 (`_WRN_SGP_BACKUP_AGE`, count 1); which module owns which chunk depends on
  the old image's construction order. Bytes 0x500 onward hold a 00..ff test pattern (earlier flash-tier runs).
  SPI: 1 MHz holds the loop ~8 ms per 1 KB, 8 MHz ~1.5 ms; requests round down (20 MHz runs at 12, 40 at 24).
- **B1 / REPORT 7 item 1 (C-stack).** 200 B per await level in a task; at depth 28 (the product's chain) 3 plain
  calls of headroom remain; depth 32 fails. Measured under `mpremote run`, a few frames deeper than frozen `main.py`.
- **B4 (sensors).** VOC `vocalgorithm_process()` 16.2 ms avg, 31.9 ms worst, 352 B per sample (host: 0.25 ms, 0 B).
  SGP40 after an unknown command: ETIMEDOUT for ~0.5 s, recovered in 528 ms. SCD30: data-ready gap median 2,143 ms at
  interval 2 s (max 2,250), longest not-ready run 20 polls at 100 ms; stored: offset 4.00 C, altitude 0, ASC off,
  FRC 400; no error at I2C timeouts 200 ms ... 1 ms. General call: bus 0 NAK, bus 1 acked, BMP settings kept.
  ISL29125 probes (extras2): all scenarios DONE, 23 range switches, no logged errors.
- **I2C faults (B4/B8, F.2/F.3).** A held line never hangs a transfer: it returns at the configured timeout (50.9 ms,
  200.9 ms). After a mid-transfer timeout the controller fails exactly one more transfer; re-construction fixes it at
  once, `clear()` and `scan()` do not. So a fault costs two timeouts (~100 ms bus 0, ~400 ms bus 1). The driver's bus
  clear behaves as designed (status 1/3/4). `scan()` is soft-I2C on rp2 (`machine_i2c.c:127-144`): an accidental bus
  clear, and the phantom 0x08 after a held SDA is its artefact.
- **F.3 stall rows (SPECIFICATION).** I2C up to 201 ms per failed transfer on bus 1; flash write 70-207 ms loop block
  with 35-39 ms interrupts off per sector erase (W25Q16JV tSE typ 45, max 400 ms); `gc.collect()` 9.6-25.5 ms (~7 us
  per live object); CRC 462-497 us/byte on rp2 (35x the host); VOC above; Wi-Fi `active()` up to 0.58 s, ~0.97 s after
  `deinit()`; `getaddrinfo()` blocked 6.9 s (stays out of `src/`); trigger latency behind a 20 ms hog ~1.6 slices;
  LAN receive load unbounded (5.9-7.97 s, one watchdog reset; accepted by the owner).
- **Resources.** 16 `Timer()` per program, dev builds ~12. UDP sockets: 4 with the station, **2 with the hotspot up**
  (captive DNS plus one DNS or NTP client fit, a third does not). TCP 9 sockets, 8 listeners; ten vanished clients
  briefly exhaust the pool; each is reclaimed in ~15 s (`MICROPY_PY_LWIP_TCP_CLOSE_TIMEOUT_MS` 10 s), no leak.
- **B7 (NeoPixel).** The WS2812 held its state through every Wi-Fi burst (above). `write()` 129 us for one LED.
- **Platform facts.** `Timer` orphaned then collected stops (F.1 on silicon); `ThreadSafeFlag` sets coalesce; Pin IRQ
  loses nothing at 200 Hz through a busy loop or a collection; `I2C`/`SPI` `deinit()` no-ops on silicon (F.5.1);
  json floats round-trip; heap 187,904 B, MemoryError text "memory allocation failed, allocating N bytes";
  `network.country()` keeps any two characters in MicroPython itself, so its "readback" says nothing about the chip
  (corrected 2026-11-02, `RESEARCH_20261102.md` 8).
