How it works now: the store's reset() writes the state it leaves before it clears RAM. If the pause refuses that write, RAM, the count and the chip all stay as they were and the answer is False. The write is refused whether the pause is caught up front or lands while the write waits on `_write_lock` or `_op_lock`. `_paused()` is read right after the write, with no await between. After the pause, the next entry's write persists the old history plus that entry. Any other failure (lost chip, fault, no chunk) clears RAM as today, returns False and prints "History reset write failed!". The RAM-only base class clears at once and returns True.

Decisions (agent, 2026-10-20):
- The image carries the entries kept since the reset began, with their count, as today's image does: two wrapping counters (`_kept`, `_counted`) and min() with `_err_count`.
- A repeat of the newest code while a reset is in flight, before anything new is kept, is marked (`_reset_repeat`) rather than appended: a reset that clears keeps that slot; a refused one leaves no doubled slot (owner's "just don't repeat the same error in the slots").
- On a non-pause failure the failing-write run flag is cleared only if the run started before the reset.
- `_WRITE_GEN_MAX` renamed `_WRAP_MAX` (no meaning change). The reset writes through `_write(kept, counted)`, so normal writes get no extra coroutine.
Effect per mode: STA, AP: ResetErrors during mempause clears nothing, also when the pause lands mid-write. Silent, Off: not reachable (no REST). USB: out of model, same code.
