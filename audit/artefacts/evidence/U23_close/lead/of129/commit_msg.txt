U23 lead: a failed hotspot-window timer arm counts as a hardware failure (OF-129)

In the hotspot mode, _hotspot_client_absent() now treats a failed arm of the
hotspot-window timer (_arm_hotspot_timer() returning False: alarm-pool
exhaustion, ENOMEM, or an allocation failure) as the iteration's WLAN
hardware failure. Before this change the arm was persisted as TIMER and
retried every 5 s without feeding the streak, so the window never ended and
STA was never retried until a reboot or a credentials resubmit. The streak
now climbs one step per no-client tick, through the device rung (the AP
re-selected), to the give-up (GIVE_UP, WLAN_GIVE_UP). The supervisor
restarts the task, whose start leaves the hotspot through
_leave_hotspot_mode() and starts a fresh STA streak with the hotspot
available once more, so a router back after a power loss is rejoined.
Repeated task ends charge the task budget, which reboots. A later tick that
arms the window heals the streak one step per clean iteration, as before.
The new comment follows the silent mode's failed-arm comment word for word
(one rule, two sites). That comment keeps its own actor and date.

Tests (tests/test_asy_wifi_service.py, 261 -> 264, all three seen failing
first on 202a118's code):
- test_a_failed_window_arm_is_the_iterations_hardware_failure: with OSError
  and with MemoryError, each failed tick sets the flag, and the two failures
  leave one TIMER slot counting 2. Once the pool has room, the tick arms the
  window once and clears the flag.
- test_integration_a_hotspot_window_that_cannot_be_armed_ends_the_task_and_its_restart_retries_sta:
  on the hotspot radio, the three no-client ticks start from streak 0, 1
  and 2, and the task gives up at max_module_error + 1. The restart runs
  with the pool still exhausted and the router back: it leaves the hotspot,
  links on a new STA interface with the stored settings, and starts a fresh
  streak with the hotspot available. The restart half guards unchanged code
  and passes on its own.
- test_integration_a_window_arm_that_succeeds_later_heals_the_streak: the
  streak runs 0, 1, 2, 1, 0, 0 across the ticks, the window is armed once,
  and the task keeps running.
_hotspot_client() takes max_module_error. The twin's Timer has no
arm-failure model, so no twin file can pin this behaviour; the unit tier
pins it.

Owner decision (owner, 2026-10-13: "Take option b for 2"), on the question asked in session in the U22
report: "OF-129: should a failed hotspot-window timer count as a hardware failure? The case: in the
hotspot mode, if the window timer cannot be armed (alarm pool exhausted), it is retried every 5 s and
logged, but the window never ends. STA is then not retried until a reboot or a credentials resubmit.
Every device is affected; the unit stays reachable on its hotspot. (a) As is. (b) Count it like the
silent mode does: it feeds the streak, then the task restart, then the budget's reboot." The owner's
follow-up, answered before the decision: "this means that currently the window timer continously fails,
the Hotspot never ends, and option b makes it try to restart the task and if unsuccessful reboots, like
normal modules do?"
